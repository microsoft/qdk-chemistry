.. _release-v2.4.0:

==========================
What's New in Version 2.4
==========================

Version 2.4 adds DUCC downfolding, matrix product state storage, auxiliary-basis
data, more general two-electron integrals, and new quantum-walk circuit paths.
Python bindings move to nanobind and require Python 3.11 or newer.
See :ref:`v2-4-compatibility` before upgrading existing data or integrations.

This release includes the 2.3.1 fixes to dependency metadata, Python/Q#
interoperability, and batched SOSSA lookups with qubit reuse.

DUCC Effective Hamiltonians
===========================

``effective_hamiltonian_constructor`` / ``qdk_ducc`` is the first bundled
implementation of the downfolding interface introduced in 2.2.
It constructs a double unitary coupled-cluster (DUCC) effective Hamiltonian
from real singles/doubles amplitudes over an orbital window and a smaller
target-space index set :cite:`Bauman2019,Bauman2022`.

Restricted closed-shell and unrestricted open-shell references are supported,
including frozen-core windows. Alpha and beta orbital counts must match in
the input window and in the nonempty target, although their occupations and
unrestricted selections may differ.
Target indices are absolute molecular-orbital indices, not offsets into an
active-space array.

The ``level`` setting selects bare downfolding (0) or commutator corrections
(1 or 2, default 2). The returned Hamiltonian retains scalar, one-body, and
two-body terms, with the external-space contribution already included.
Do not correlate those external orbitals again.

Integral Symmetry and Electronic Structure
==========================================

Native correlation and qubit mapping now handle Hermitian two-electron
integrals with four-fold rather than full eight-fold symmetry, as arise in
downfolded Hamiltonians. The native qubit mapper treats symmetric and
antisymmetric excitation-pair contributions separately; it no longer assumes
ordinary Coulomb-integral symmetry for every Hamiltonian.
See :doc:`../user/comprehensive/algorithms/qubit_mapper`.

Four-center transformations and Cholesky materialization preserve the
permutation symmetry of ordinary Coulomb integrals, including in diffuse
bases. Native ROHF also handles linearly dependent AO bases by optimizing in
the retained, potentially smaller MO space. Empty closed, open, or virtual
subspaces are allowed; an insufficient retained space for the requested
occupations fails explicitly.
See :doc:`../user/comprehensive/algorithms/scf_solver`.

PySCF reference conversion now uses the supplied Hamiltonian's stored
one-electron integrals, two-electron integrals, and scalar core energy in
the MO basis instead of recomputing molecular Coulomb integrals.
The resulting reference has no AO basis. Methods that require one, such as
PySCF density fitting, need a molecule constructed separately from the basis.
Eight-fold symmetry is still required for restricted and same-spin PySCF
integrals; the opposite-spin block requires pair symmetry.
General downfolded tensors and active-space effective Hamiltonians are not
supported by this conversion.
See :doc:`../user/comprehensive/algorithms/hamiltonian_constructor`.


Auxiliary Basis Data
====================

:class:`~qdk_chemistry.data.AuxiliaryBasis` is an independent basis value,
and :class:`~qdk_chemistry.data.AuxiliaryBasisCollection` groups such values
by ``JFit``, ``JKFit``, ``RIFit``, and ``CABS`` roles.
Primary and auxiliary bases are built against the same structure; neither
the primary basis nor the wavefunction stores the collection.

   :language: python
   :start-after: # start-cell-loading-with-aux
   :end-before: # end-cell-loading-with-aux

``resolve_auxiliary_basis`` permits ``JKFit`` to satisfy ``JFit``, but not
the reverse. ``with_auxiliary_basis`` returns a new collection with a role
added or replaced. Both individual bases and collections support independent
JSON/HDF5 serialization.

These are data interfaces for algorithms that explicitly accept auxiliary
inputs. Constructing a collection does **not** enable density-fitted SCF.
See :doc:`../user/comprehensive/data/basis_set`.

states, including symmetry-blocked site tensors, orbital ordering, and an
optional orthogonality center. They integrate with

Quantum Walks and Circuit Composition
=====================================

Standard SOSSA QPE
------------------

``controlled_circuit_mapper`` / ``sossa`` completes and controls the SOSSA
walk for native standard QPE. Only its reflections are controlled; PREPARE
can run without a controlled implementation.

block-encoding path used by unary QPE.

not a chemical-accuracy setting. SOSSA requires canonical, untapered, blocked
Jordan-Wigner ordering and reports total energies, including the core energy.
Iterative SOSSA QPE remains unsupported because its feedback cannot separate
the two walk-phase branches of a system eigenstate.

Native standard and iterative QPE now initialize compatible shared
phase-gradient registers once and reuse them across state preparation and
controlled powers. The Qiskit builders do not initialize this shared suffix.
See :doc:`../user/comprehensive/algorithms/qpe_circuit_builder` and
:doc:`../user/comprehensive/algorithms/circuit_mapper`.

SOSSA lookup tradeoffs
----------------------

The SOSSA mappers expose the lookup controls added in 2.3.1:
``max_givens_rotation_batches`` trades a smaller angle register for more
lookup passes; ``lookup_method`` selects plain lookup, clean QROAM, or
``"dirty_select_swap"`` with borrowed qubits; and ``max_swap_address_bits``
caps each swap network. These settings apply to both controlled and
uncontrolled SOSSA mapping.
See :ref:`sossa-mapper-settings` for defaults and scope.

LCU SELECT and Hubbard phasing
------------------------------

LCU PREPARE-SELECT-PREPARE mappers now default to unary-iteration SELECT.
Set ``select_method="multi_controlled"`` to retain the earlier construction:

   :language: python
   :start-after: # start-cell-lcu-select
   :end-before: # end-cell-lcu-select

Unary iteration is implemented without recursive Q# calls.
For LCU circuits using alias-sampling or QROM PREPARE, simulation and resource
estimation work, but QIR export and circuit serialization remain limited by
the Q# compiler's lowering of measurement-based lookup uncomputation.
Use ``dense_pure_state`` PREPARE when QIR export is required.

The Hubbard plaquette controlled mapper now defaults to
``hamming_weight_phasing_method="catalyst"``: generalized phase gradients
are prepared for the interaction and hopping layers and reused.
``"rz_ladder"`` retains the per-place-value rotation alternative;
``use_hamming_weight_phasing=False`` disables phasing.
The Hubbard resource-estimation notebook demonstrates the new path.

Repeated Pauli-evolution callables and Q# sequential composition now retain
adjointability, so they can be reused in inverse circuit constructions.
This does not make measurement-bearing operations reversible.

Compatibility and Migration
===========================

Sparse Hamiltonians
-------------------

``SparseHamiltonianContainer`` uses schema ``0.3.0`` and reads stored
two-body entries literally, with unstored positions zero.
Migrate older files with ``python -m qdk_chemistry.migrate``.
For Hermitian legacy data, migration expands the old eight-fold symmetry
representatives and rejects conflicting values in a permutation class.
Non-Hermitian data keeps its entries as stored.

Sparse maps constructed in code are not file-migrated. A lone representative
in a Hermitian container still expands with a deprecation warning, but a
class with multiple stored members is read literally.
Use ``SparseHamiltonianContainer.expand_symmetry_representatives`` or
explicitly provide all intended entries. Partially populated classes that
previously relied on mapper-only expansion can change results.

Older four-center and Cholesky files can retain transformation roundoff
that violates permutation symmetry. Rebuild affected Hamiltonians from
their orbitals when FCIDUMP export or PySCF conversion rejects them.
See :doc:`../user/migrating-data-files`.

Execution and data loading
--------------------------

The full-state QDK executor rejects QIR supplied directly or restored from
files unless ``allow_external_qir=True``. Enable this only for trusted
producers: execution is not sandboxed and the flag does not validate QIR.
Internally compiled Q# and OpenQASM do not need this opt-in.

Restored remote jobs use current runtime connection configuration, not
connection parameters saved in the job file. Use ``Job.attach_backend``
when a restored job needs an explicitly configured backend.
Sparse Hamiltonian deserialization, basis extraction, and cache paths also
gain stricter validation.


Python Packaging and Native Builds
==================================

Python 3.10 support is removed. Standard, GIL-enabled CPython 3.11 and newer
share one ``cp311-abi3`` QDK Chemistry wheel per platform and architecture.
Pip installs the interpreter-specific ``nanobind-backend`` package alongside
it; that backend and other dependencies must support the chosen interpreter.
This is not a promise of free-threaded Python support.

The bindings now use nanobind rather than pybind11. Source builds use
``scikit-build-core>=1.0`` and ``nanobind>=3.1.0``, and the runtime also
requires ``nanobind-backend>=1.0``. Native extensions that interoperate with
the former pybind11-bound classes need to be rebuilt and adapted to nanobind;
the ABI change is not a drop-in replacement for such add-ons.
Generated native-module type stubs remain generated on first import.
The minimum QDK dependency increases from ``1.33.1`` to ``1.34.0``.

Supported wheel platforms remain Linux x86-64/Arm64, macOS Arm64, and Windows
x86-64/Arm64. Optional-dependency restrictions remain in effect: PySCF is
unavailable on native Windows; MCP, Azure Quantum, Discovery, and the Qiskit
stack have Windows Arm64 exclusions; OpenFermion requires Python below 3.14;
Qiskit Aer is omitted on Linux Arm64 with Python 3.14.
See the `installation instructions
<https://github.com/microsoft/qdk-chemistry/blob/main/INSTALL.md>`_.

Native builds add SeQuant symbolic algebra with BTAS tensor evaluation,
used by DUCC. No-fetch builds can use an installed SeQuant prepared through
``cpp/cmake/sequant`` with the repository's pinned dependencies and patches.
MACIS adds optional single-rank C++ ASCI execution contexts for numerical
search and diagonalization; omitting a context retains the CPU path.
This does not add a new Python ASCI backend.
ASCI also guards excitation constraints that cannot be satisfied.

CI changes parallelize wheel tests, reduce cache pressure, and isolate
reporting from untrusted build artifacts. Tutorial checks cover visualization
outputs and sampled-distribution invariants rather than fixed IQPE counts.
